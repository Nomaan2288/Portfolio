Section 01

Executive Overview & The Core Problem

Online reservation systems represent one of the classic crucible problems in software engineering. When thousands of concurrent clients attempt to reserve finite physical inventory (such as numbered cinema seats, concert slots, or VIP tables) within seconds of ticket release, traditional naive database queries immediately collapse under race condition hazards.

BookMyEvent was conceived and developed from first principles to resolve these exact failure modes. Rather than relying on third-party opaque monoliths, the platform implements a modular, ACID-compliant reservation pipeline with defensive concurrency controls, end-to-end user auditing, dynamic venue grid builders, and real-time administrative oversight.

Architectural North Star
Zero double-bookings under peak concurrency, deterministic state recovery upon payment drop-off, sub-150ms indexed search queries across dynamic event catalogs, and cryptographic proof-of-reservation for ground verification.
Section 02

System Architecture & Tech Stack

The system employs a battle-tested layered MVC architecture built on top of Java 17 and Spring Boot 3. Data access is backed by MySQL 8.0 InnoDB, deliberately leveraging row-level locking capabilities, transaction isolation levels, and explicit indexing.

Authentication, Role Separation & OTP Recovery

Security begins at user admission. The platform separates client identities into two mutually exclusive domains: Public Customers and Executive Administrators. Every incoming request passes through an authentication interceptor verifying active session tokens.

Minimalist, high-contrast authentication interface. Validates credentials against BCrypt-hashed password digests stored in MySQL. Automatically routes authenticated users according to their permission grants: regular users to event discovery, administrators to executive dashboards.

  • HTTP-only session tokens safeguard against cross-site scripting (XSS) token theft.

Section 05

The Concurrency Challenge: Real-Time Seat Locking

Here lies the true technical heart of BookMyEvent. Consider the scenario: User A and User B click on "Seat C-14" at the exact same millisecond. If the system simply checks availability at the moment of payment submission, one user will pay for a ticket that has already been taken.

To eliminate this, BookMyEvent implements a Two-Phase Transient Seat Locking Algorithm:

SeatLockRepository.java — Pessimistic Lock Query MySQL 8.0
// Step 1: Acquire exclusive row lock on seat for event slot
SELECT * FROM venue_seats
WHERE seat_id = :seatId AND event_slot_id = :slotId
FOR UPDATE;

// Step 2: Validate state — must be AVAILABLE or expired hold
if (seat.getStatus() == SeatStatus.AVAILABLE || seat.isHoldExpired()) {
  seat.setStatus(SeatStatus.LOCKED);
  seat.setLockedByUserId(currentUserId);
  seat.setLockExpiresAt(Instant.now().plusMinutes(10));
  seatRepository.save(seat);
}
https://bookmyevent.internal/booking/seats?slot=1042
Figure 3.1 — Interactive Venue Seat Matrix with Real-Time Lock States Concurrency Algorithm

Color-coded seating matrix visually segmenting seats into Available (Green), Selected by User (Blue), and Locked / Sold (Grey/Disabled). Upon selection, seats enter a 10-minute countdown timer. If checkout is abandoned or expires, a scheduled background cron automatically restores seats to the public pool.

Section 09

Key Engineering Takeaways & Architectural Lessons

Designing and shipping BookMyEvent yielded foundational insights into building resilient distributed-style applications on top of relational database primitives:

1. Pessimistic Row Locking Beats Optimistic Locking for Scarce Goods
For scarce physical seats under extreme flash-sale concurrency, optimistic locking causes massive retry storms and bad user UX as hundreds of users fail at checkout. Enforcing a transient pessimistic lock row hold (`FOR UPDATE`) for 10 minutes gives users deterministic guarantees.
2. Database Indexes Must Mirror Business Query Vectors
Event filtering by genre and date requires composite multi-column indexing. A single poorly designed index can turn a 20ms query into a 4-second full table scan when sorting by release dates.
3. Defensive Ground Verification is Mandatory
Digital confirmation screens are trivial to forge with client-side DOM tampering. Generating cryptographic SHA-256 signatures embedded directly into high-density QR codes ensures bulletproof validation on venue turnstiles.
